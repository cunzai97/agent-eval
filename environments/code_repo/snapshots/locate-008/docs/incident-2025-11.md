- 参与：SRE 值班、流量治理组、计费接入组

## 1. 结论（已确认，不要再重复排查）

1. 本场景共 100 条请求，**放行 48 条，放行率 0.48**。
2. 损失**全部**来自 epoch 配额闸门：`denied_by_quota = 52`、`denied_by_bucket = 0`。
   换言之，**本场景里全局令牌桶从来不是瓶颈**：`BUCKET_CAPACITY = 14` 始终有余量，
   任何"桶被抽干导致误拒"的解释都不成立，值班同学不必再往 `bucket.py` 方向排查。
3. epoch 配额在租户间按权重**向下取整**分配（#3620 口径），再按各租户本 epoch 的实际
   需求封顶，所以**单个 epoch 内分配出去的配额之和不会超过 `CAP_PER_EPOCH = 8`**。
   小权重租户在余数分配前被截断为 0 属于**预期行为**，是设计上的保守取值，不是缺陷。
4. 两个物理常量已与 `ratelimit/config.py` 逐条比对，自 #3620 起未变：
   `BUCKET_CAPACITY = 14`、`REFILL_INTERVAL_S = 4`；`CAP_PER_EPOCH = 8` 同期确定后也未动。
