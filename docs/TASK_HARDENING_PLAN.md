# 软题加难方案

> 针对 2026-09-20 审计出的 18 道"无区分度"题目。目标：把它们从 84–94% 拉进可区分区间，
> 沿用户指定的两个轴向——**思考深度**与**多步执行**。
> 硬约束：加难后必须仍可解，且必须有**负向对照**证明加难真的有牙齿。

---

## 0. 判定口径

参照系固定为**现有 runs/ 里的 31 个模型**（全部 27B/35B 级，总分 51%–92%）。
本方案的"过简"一律指"对该群体无区分度"，不做小模型校准，也不为低龄段保留这些题。

因此判定规则是单一的：

| 观测 | 结论 | 动作 |
|---|---|---|
| 弱档（bottom-10，总分 ≤75%）通过率 ≥83% | 对该群体无区分度 | **按下文加难** |
| 全部试过的模型都至少做对过一次 | 无淘汰力 | 优先加难 |

18 道目标题全部落在"加难"这一格，无需再分诊。唯一保留的口径提醒：加难后的通过率
只在同一 27B/35B 群体内解释，换群体时重新定标。

## 1. 已定位的结构性成因（决定了加难往哪儿使力）

对照实验：`code_repo` 家族里只有 008 / fix-007 / fix-008 挂了 post-run 隐藏测试
（`evalkit/envs/hidden_tests/`），它们通过率 **0% / 75% / 6%**；其余 13 道只考可见测试的
debug/fix 题分布在 **69–94%**，其中 10 道 ≥80%（debug-005 与 fix-002 是例外，各 69%——
它们的难度来自 snapshot 本身，见第 4 节）。隐藏测试不是唯一变量，但它是目前最强的一道闸门。

根因：**"让可见测试变绿"就是全部标准**。这分不清"修对了根因"和"绕过了断言"——
模型可以特判、可以只改被断言到的分支、可以在调用点打补丁而不是在契约定义点。
可见测试是**充分性检查**，而题目想要的是**必要性检查**。

所有加难手段都应服务于一个原则：**给模型一个"看起来对但实际错"的捷径，然后让检测必然抓住它。**

## 2. 轴向一：思考深度

### D1. 隐藏泛化测试（最高 ROI，优先做）

复用现成机制，给 `code_repo` 快照补 `evalkit/envs/hidden_tests/<snapshot>.py`，
并在 YAML 加断言：

```yaml
- type: state_assert
  expr: "state.hidden_tests.passed == state.hidden_tests.total and state.hidden_tests.total >= 6"
```

隐藏用例的写法要求（这决定加难是否有效）：

- **必须包含可见测试没有覆盖的边界**，且该边界恰好是"错误修法"的分水岭。
  例：`debug-004` 的状态规范化，可见测试只测了 `pending → active`，隐藏用例补
  `pending → PENDING`（大小写）、`"" → None`、以及"已经是 active 的记录不能被降级"。
  只在比较处 `.lower()` 的特判会挂在最后一条。
- **专抓"在调用点打补丁"**：构造一个绕过被修补调用点的第二条路径。
- 数量 5–8 条。debug-008 的 5 条已经把全套模型压到 0%，别一上来就堆到 20 条。

> ⚠️ 副作用：`total >= N` 会让题变得极脆（008 就是 0/34）。建议门槛设 `>= 5` 起步，
> 观察一轮再调。**宁可 20% 也不要 0%**——0% 的题和没出题一样，没有梯度信息。

### D2. 近似诱饵（near-miss decoy）

在 snapshot 里加一个**与真正根因症状几乎一样、但成因不同**的第二处缺陷，
断言要求模型区分二者。locate 家族尤其需要——locate-001（34%）比 002–006（85–94%）难的
实质差异只有两点：001 多要求 `grep_calls >= 1`（7 条检查 vs 003 的 6 条），
且它的调用链更深、诱饵更像。把这两点复制到全家族即可，不必重新设计。

```yaml
# locate 题：answer 里增加 excluded_symbol 字段，要求指名"像但不是"的那个
- type: state_assert
  expr: "state.answer_json == {'file': 'x/y.py', 'symbol': 'true_cause', 'decoy': 'near_miss_fn', 'cause': '...'}"
```

`cause` 枚举保留，加一个 `decoy` 键。模型只答对真正因不够，还得认出诱饵。

### D3. 跨文件不变量

把同一个契约在两个文件里各实现一遍（现状 debug-008 已有 scheduler/transport 双owner 的雏形），
只修一处必挂。断言要求两个文件同时被改：

```yaml
- type: state_assert
  expr: "all(p in state.files_changed for p in ['a/x.py', 'b/y.py'])"
```

注意：这条单独用无效——模型可以乱改两个文件。**必须和 D1 搭配**，让它必须改对。

### D4. 冲突信息源（现成范式，扩到非 memory 题）

memory-loop-003 已验证该手法有效：种一条**过时的持久记忆**与当前 `source_of_truth` 文件冲突，
模型必须以文件为准并原位修正。把这个模式搬到 debug/fix 题：**仓库里留一份过时的
`docs/contract.md`，与代码真实契约矛盾**，且要求模型在 `answer`/结论里指出文档已失效。

### D5. 数值与顺序的确定性要求

data-pipeline-005 的"确定性 Top2"就是这个路子。扩展：并列时按次级键排序、空分母显式输出
`NA` 而非跳过、浮点定点小数位数。便宜且必然淘汰"近似正确"的解。

## 3. 轴向二：多步执行

### E1. 产物链（artifact chain）——把"一步写对"变成"多步互锁"

现状 data_ws 题只断言最终 CSV 内容，模型可以在一次 `run_python` 里全算完。改成三段互锁：

```yaml
# 1. 必须先产出一个中间清单，且被后续脚本读取
- type: state_assert
  expr: "'out/decisions.json' in state.files and state.files['out/decisions.json']['rows'] >= 1"
# 2. 最终产物必须由脚本生成，不得手写
- type: state_assert
  expr: "state.artifact_generated_by_run == True"
# 3. 强制顺序
- type: order_of
  tools: [read_file, write_file, run_python, write_file, run_python, done]
```

实现要点：环境需要新增一个 `state` 字段记录"每个产物是否由某次 run_python 的 stdout/写文件
行为产生"。`data_ws` 已经统计 `run_python` 调用，加一个产物来源映射即可。

### E2. 证据计数器门槛

code_repo 环境的 `state` 已暴露 `grep_calls` / `test_runs` / `files_read`。当前软题只用
`test_runs >= 1`，太松。参照 locate-001（6 条检查、34%）而非 locate-003（5 条、94%）：

```yaml
- type: state_assert
  expr: "state.grep_calls >= 2 and state.test_runs >= 2 and len(state.files_read) >= 4"
- type: tool_used
  name: run_tests
  min_calls: 2
```

`test_runs >= 2` 的语义是"改之前跑一次、改之后再跑一次"，用计数强制这个流程，零额外实现。

### E3. 只读与副作用约束（liberty 已验证）

`state.modified == []`、`state.source_unchanged`、`generated_bytes <= max_generated_bytes`、
`runner_stdout_bytes <= 20000`。这套能逼迫"有界探查 + 脚本化处理"，而不是把数据读进上下文硬算。
对 data_ws：给一个**故意超过上下文的大输入**（几 MB CSV），并禁止全量 read_file。

### E4. 中途状态变更

在模型 `run_tests` 第二次调用后，由环境注入一个无关文件的改动或一次瞬时失败，检测模型是否
把它误当根因、或是否重跑确认。**这条实现代价最高，放最后做。**

## 4. 真实失败模式库（来自本人历史 Qoder 会话，非虚构）

上面 D1–D5 / E1–E4 是通用手段。这一节是**弹药**：每一条都是实际发生过的失败，
比凭空构造的诱饵更可能命中模型的真实弱点。标注了核实状态。

### 已逐条核实

**P1. 默认参数掩盖的部分迁移**（`multica-core-offline/src/main.cpp`）
`log_activity` 共 **22 个调用点**，只有 **8 处**补了显式 actor，其余 **14 处**继续吃
默认值 `actor_id = "local-user"`（定义在 618 行），含 689 行的 agent run 完成/失败事件。
签名带默认值 → 漏改的地方**照常编译、冒烟测试全绿**，审计归属长期是错的。

> 出题：题面"让所有操作日志归属到真实操作者"。隐藏测试对每种实体各造一条事件，
> 断言 `actor_id` 均非默认值，**特别覆盖 run/后台任务这条最容易漏的路径**。
> 这是 D1 的完美素材：特判几个调用点必然挂。

**P2. 跨副本扇出漏一处**（同上仓库）
新增一种实体（`skills`/`views`）需要同步到 ≥8 处：建目录、`seq` 迁移计数器、
`export_bundle`、base/extended/v3_kinds 三张清单、`/api/state` 的两个载荷、CLI help、
前端渲染器。漏掉任意一处不会报错，只会让该实体**静默地从导出里消失**。

> 出题（多步执行）：给"新增实体类型 X"的规格，断言 `export → import → /api/state`
> 三处都含 X，且迁移后旧 bundle 仍可读。检查成本极低，区分度极高。

**P3. 复述式结论：与当前状态脱钩**（`hidden-orders-m0/games/ab/`）
`career-ridge-vision.md` 第 11 行与第 17 行的"战后日记"**逐字节相同**，却属于两局不同对局。
`career-27b-warm.md` 更直接：记分板 `控制11:12`，日记写"当前比分10:10"；
`控制8:13` 那局写"当前B领先4分"。**模型在生成摘要时没有读当前状态。**

> 出题：要求最终 `answer`/产物里必须含**只有本局才知道的具体数值**（turn id、控制分、
> 剩余单位数）。断言分两层：(a) 数字与环境 ground truth 相等；(b) 与上一次作答的文本
> 不得相同。这是全新的检测维度，现有 40 题里**没有任何一题**测这件事。

**P4. 重复同一失败动作不收敛**（`27b-warm-game-1.txt`）
弓兵 A7 射 B1 连续 4 回合 `[落空]` 仍重复下令；B1/B2/B6 三支队伍被派往同一格 `(8,5)`
互相 `[阻挡]`。这与我在 ternary-bonsai 的 `data-pipeline-006` 里看到的调试螺旋
（8 次 `run_python` 反复验证同一个矛盾）是**同一个失败模式**。

> 出题：新增检查类型 `no_repeat_failure`——同一工具 + 同一参数在收到 error 观测后
> 再次出现即计一次，超过 N 次判失败。实现只需扫 `traj.steps`，几十行。
> 这条直接把我们审计出的头号软性失败模式变成**打分项**而不只是事后分析。

**P5. 元数据撒谎**（`a-share-sim`）
`meta('adjust')` 声称 `hfq`，实际数据是链式复权（`adjusted=2`）；import 时写
`{"schema_version":1}` 而 HTTP 响应报 `schema_version:4`；`export_bundle` 与 `/api/state`
把 `users`（含 salt + SHA-256 哈希）一起送到浏览器和备份文件。
**这类错误在任何输出里都看不见**，只有交叉核对才发现。

> 出题（data-pipeline）：给一份单位/口径标注错误的输入 CSV（如表头写"千元"实为"元"、
> 写"含服务费"实为净额），断言产物与**真实语义**一致而非与表头一致。诱饵就是"照抄表头"。

### 子代理报告、方向可信但未逐行核实

**P6. 静默截断导致假结论**：`[:4000]` 把 JSON 从记录中间切断；trace 结果截到 800 字符使
`json.loads` 失败后 `continue`，得到 0 行 → 误判"全市场无人创新高"（实际 35 只）。
> 出题：工具返回值刻意截断并带截断哨兵，断言模型必须翻页取全或显式声明"这是下界"。

**P7. 两条独立路径必须一致**：Tier-2 只取 80 根 K 线导致 `new_high_250d` 永不触发；
靠"Tier-1 计数 == Tier-2 计数"这条约束才抓到。wargame 引擎同样要求"三路一致才敢报数"。
> 出题：snapshot 里预置两条推导路径给出矛盾结果，断言模型必须调和而不是挑一个用。

**P8. 退化基线伪装成能力**：`noop` +0.0% / `hold_etf` +5.0% / `momentum` −20.1%；
某策略 +18.87% 只是押中单一龙头，等权全市场 −0.37%（中位 −3.76%）。
> 出题：要求产物里必须含一个**同风格对照**，断言其存在且数值自洽，否则判 fail。

**P9. 小样本外推**：相关系数随窗口拉长 +0.354(19d) → +0.295(22d) → **+0.015(37d)**。
> 出题：给一段"看似有信号"的小样本，断言结论里必须包含稳定性检查或撤回。

**P10. cwd 失忆 / 工具错误后硬重试**：`bash tests/smoke.sh` 因 CWD 不对连续失败两次才
想起 `pwd`；`Write failed: File has not been read yet`、`Edit 0 occurrences` 各重复两次。
> 这条我自己今天也踩过（`cli.py` 的 CWD 不匹配）。出题：工作区根与默认 CWD 故意不同，
> 断言 `run_bash` 用绝对路径或先探明 CWD，且同类错误调用不得重复超过 1 次。

## 6. 验收协议（每道改过的题都必须过这两关）

沿用 debug-008 上验证过的参考解方法，但**增加负向对照**：

1. **正向：参考解必须全项通过。** 手写一个正确实现，跑 `run_checks`，要求 `passed == True`。
   做不到就说明门槛定高了（008 现在就是 0/34，虽然可解但没有梯度）。
2. **负向：捷径解必须失败。** 专门写一个"让可见测试变绿但根因未修"的投机实现，
   要求它被 D1/E1 抓住。若它也通过，说明加难无效，只是加了步骤数。
3. **回归：重放历史 state。** 对只改断言、不改 snapshot 的题，用现有 33–42 份
   `state.json` 重放 `run_checks`，确认通过数按预期变化（memory-loop-004 那次修复
   就是这么验证的：0 → 5，且 7 例真改写仍被拒）。
4. **重跑定标**：改完的题在现有群体内取三人面板（1 强 / 1 中 / 1 弱档，均为 27B/35B 级）
   各跑 3 次，目标 `hard` 落在 **20–55%**，`medium` 落在 **55–80%**。

> 排行榜影响：`evalkit/fingerprint.py` 把题目规范、snapshot、隐藏测试、evaluator 与
> agent-loop 语义一起计入 task fingerprint。本次已发生的两处改动（agent_loop 的 token
> 口径、memory-loop-004 断言）**已经**让旧 run 不再进当前榜单——这是预期行为，
> 但意味着加难完成后需要重新建基线，历史通过率不能直接对比。

## 7. 预算同步

token 口径改为增量累加后，同样的 `max_tokens` 预算实际宽松了约 2.2 倍（单题最高 5.4 倍）。
多步执行类加难会显著增加步数，因此：

- `max_steps`：产物链类题目从 28–30 提到 40 左右，避免流程还没走完就 `max_steps` 截断。
- `timeout_s`：V100 上 ~43 tok/s，40 步 × 中等输出会逼近 900s。加难题建议同时把
  被测模型的 `timeout_s` 和题目 `timeout_s` 一起复核，否则 `timeout` 会伪装成"能力不足"。
- `max_tokens`：先按新口径实测一遍参考解的真实新增量，再定预算，别沿用 64000。

## 8. 跨题通用增补（先建机制，再逐题受益）

这三条不属于某一道题，建好后全套 40 题都能挂：

- **N1 数字溯源断言**（源自 P3）：`state_assert` 支持一个内置助手，从模型 `answer`/产物的
  自由文本里抽数字，与环境 ground truth 比对；并要求本次文本不得与上一 attempt 相同。
  现有 40 题没有任何一题检测"结论是否真的读过当前状态"，这是最大的空白。
- **N2 `no_repeat_failure` 检查类型**（源自 P4）：扫 `traj.steps`，同一工具 + 同一参数在收到
  error 观测后再次出现即计数，超 N 判失败。审计里头号软性失败模式，目前完全不计分。
- **N3 截断哨兵 + 下界声明**（源自 P6）：有界读取类工具统一返回 `truncated: true`，
  凡依赖它的产物必须显式声明取样范围，否则 fail。liberty 已有一半基础设施。

## 9. 施工顺序

1. **locate-bug-002~006**：纯 YAML + snapshot 加诱饵（D2 + E2），最快见效、零框架改动
2. **N2 `no_repeat_failure`**：几十行，建完立刻能给全部题加一条新轴
3. `shell_hidden` 验证器参数化（一处改动覆盖 script-dev 5 题 + write-cli）
4. **code_repo 隐藏测试**（D1）：debug-001~006、fix-001/004/006，优先做 **P1（默认参数

### 10.2 与方案的两处偏离

**偏离一：不做小模型定标。** 原 §0/§6 写了"三人面板重跑定标"。已确认不需要——本套件只以
现有 27B/35B 群体为参照系，小模型档位不在关注范围内。校准改用**历史轨迹回放**（见 10.3），
不额外占用 GPU 时间。

**偏离二：验收第 4 关换了判据。** 原方案要求"改完跑三人面板看通过率落 20–60%"。实际改为：

> 加难后，**历史上判对的轨迹必须有 20–60% 仍然判对**。

理由是三人面板要 27 次运行且受本地推理速度支配，而回放是确定性的、几分钟能跑完，
并且直接回答真正的问题——"我这一刀是不是把合法解也砍死了"。100% 存活说明闸门没测到东西，
0–10% 存活说明闸门过锐。

**这条判据有适用边界，用错会得出反向结论**（实测踩到，见 10.3.1）：只有当加难**没有改变
题面向模型索要的东西**时，历史轨迹才是合法样本。

- **适用**：给同一个产物加隐藏泛化用例——`debug-001/003/004`、`fix-004/006` 的 post-run 隐藏测试，
  `script-dev-*`/`write-cli-001` 的 held-out 输入。模型在旧题面下写出的脚本，本来就"应该"
  能过这些用例，过不了就是真没做对。
- **不适用**：加难同时**新增了输出字段、行为门槛，或把题面 prompt 改写得更啰嗦**。
  `locate-bug-002~006` 的回放存活是 **0%**，但这不代表它们不可解——旧题面从没要求 `decoy` 键，
  也从没要求 `grep_calls>=2 / files_read>=4 / test_runs>=1`，历史轨迹按构造必然全挂。
  这五题的真实通过率**未知**，不是 0。
  同一陷阱的隐蔽版本：给题面 prompt **补写更细的规则说明**（为了"不考提示词里没写的东西"）
  同样会让旧轨迹在新增条款上必然失败，从而把存活率压低。判存活率之前先 `git diff` 一次题面，
  把隐藏用例按"旧 prompt 已隐含 / 新 prompt 才写明"分类，只用前者算存活。

闸门只能证明"判据可满足 + 终态可重复"，证明不了"仅凭题面能唯一确定答案"，也证明不了

| 题 | 症状 | 真因 | 处置 |
|---|---|---|---|
| `data-pipeline-008` | 两次实跑都在"step 1"吃 400，`tokens=1236`，被记成 FAIL | `data_ws.read_file` 上限 200,000 字符：440,150 字节的输入一次读回 184,397 token，超过网关 99,072 上下文。**任何**模型走"先读文件"这条路都必死 | 上限收到 12,000 字符并显式给 `truncated` + `file_bytes`，工具说明写明契约；复跑 7 步 / 23,341 token PASS，先探查脚本再算规模数字，行为正是考点要的 |
| `memory-loop-005` | 模型按题面字面全对，判据全错 | runbook 第 1 条把"结算工作日"定义成"不在 holidays.md 里"，与"周一至周五"同时成立却给出 06-29 / 06-27 两个答案；第 3 条分号串三步，按字面顺序执行会剔掉 T3，而 `EXPECTED` 要它 | 只改题面定义，`EXPECTED` 一字未动；同轮把 memory 五题的"一次闭环只留一次记忆变更"从隐含写成显式契约（判据一条没放松） |

顺带把 `tools/probe_request.py` 落进仓库：按 `agent_loop` 的方式组装请求、真实回填工具观测、
把服务端**响应体**打出来。没有它，第一个缺陷会被一直记成"基建抖动 + 模型不会做"。

`locate-bug-*` 那类"样本作废"和这里的"尝试不起来"是同一件事的两种表现：**判据先于尝试**。
所以 10.2 那条适用边界要补一句——回放存活率只能在"这题真的跑得起来"的题上解释；
读轨迹是这套流程里唯一能发现"跑不起来"的环节，不能省。

### 10.9 判据口径变更（2026-09-21 用户裁定）：过程计数不再当能力代理

裁定原话：『判据可以放松，达到最终目的就行，因为有时候代码太小模型倾向直接看。
但是注意不要太松放过那些假对』。据此把**纯过程计数**降级，把防假对的职责整体交给
**结果性判据**（隐藏用例、钉死的产物数值、答案键）。三条依据都是实测来的：

| 流程形态 | 样本 | 结果性断言全过 |
|---|---|---|
| 从没跑过测试 | 10 | 0 (0%) |
| 只建基线、改完没复跑 | 4 | 0 (0%) |
| 改后复跑 + 有基线 | 81 | 30 (37%) |
| 改后复跑 + 无基线 | 8 | 4 (50%) |

所以"改完必须复跑"留着（不满足者 0/14），"改前必须有基线"删掉（测不出差异）；
locate 的 `grep_calls >= 2` 降到 `>= 1`，`len(files_read) >= 4/5` 这类**纯计数**删掉，
"必须读过某几个具体文件"与 `test_runs >= 1` 保留。`run_tests / run_bash / source_search`
的 `min_calls: 2~7` 全部取消（默认 1），`order_of [run_tests, edit_file, run_tests]`
统一改成 `[edit_file, run_tests]`。共 31 个题面、约 50 行判据。

放松的 blast radius（用录制的 `state.json` + `trajectory.json` 在新判据下精确重评，不重跑模型）：
受影响 32 题的 985 条历史尝试里，**35 条**由 FAIL 变 PASS（3.6%），其中
memory-002 +11、fix-002 +5、debug-002 +5、fix-005 +3、locate-007 +3、debug-005 +2、其余 6 题各 +1。
**这 35 条里有 17 条落在既无隐藏用例、又无钉死产物的 6 道裸题上**（debug-002/005/007、
fix-002/003/005）——它们的抽样长这样：`步5 测试1次 编辑2次 改文件['money/rules.py','money/convert.py'] 报告8绿/0红`，
看起来是真修，但**没有隐藏用例就证明不了不是门面修**。这 6 道因此列为放松的补偿性必做项，
按 fix-001 的同一配方补：隐藏用例 + 参考产物 + 一份"可见绿但改错"反例，
两道硬验收是 `audit_invariants` 报 SOLVABLE+STABLE 且反例必须仍然判负。

放松是否放过了已知假对：8 份反例全部重跑，仍然判负——
`NC-F1 3/6、NC-F2 4/6、NC-F3 2/6、NC-F4 5/6、NC-A1 4/8、NC-A2 6/8、NC-A3 7/8`，
`NC-001-facade-bypass` 可见 9/9 绿而隐藏 28/32；全 50 题两不变量复跑仍是
`SOLVABLE+STABLE 50 / 不成立 0`。

### 10.11 归因收敛（2026-09-21 用户裁定：『模型要能够重试才行，裁判还是需要的，只不过确定性的东西就不需要裁判了』）

这一节不改难度，改的是**分数记在谁头上**。两条实测前提：

**一、上游故障此前被记成能力失败。** 1,436 次已录尝试里 76 次 `termination=error`，
其中 75 次是纯机器问题（48 connection refused / 22 HTTP 5xx / 4 断连 / 1 客户端超时；
剩下 1 次 400 是已修的 read_file 上下文炸弹）。它们高度集中在 3 个跑批夜，各砸在一个模型上：

| 那一行基线 | 已录尝试 | 被机器打死 | 现记通过率 | 若记"未评" |
|---|---|---|---|---|
| Qwen3.8-27B-UD-Q4_K_XL_reason2K | 65 | 25 | 50.8% | 82.5% |
| ternary-bonsai-27b | 69 | 17 | 56.5% | 75.0% |
| Hermes3.6-35B | 117 | 28 | 53.0% | 69.7% |

按"未评"重算，31 个模型里 **19 个名次会动**。落地：`provider` 对可重试故障做指数退避重试
（默认 4 次，且**绝不吃掉本题剩余墙钟**——预算用完仍归 `timeout`），用尽后抛 `InfraError`
→ `termination="infra_error"` → `EvalResult.graded=False`；`cli.py` 聚合时未评不进分母、
单独计数并留题号原因；跑批前先探上游（`--preflight-wait-s`，默认 120s），不可达直接不开跑返回 2。

**二、裁判作为闸门的实测贡献是 345 次判词里 1 次。** 17 道带 rubric 的题逐题对比"记录判定"
与"只看确定性判据"：只有 `locate-bug-006` 翻转 1 次，而它考的是"读过几个文件"的宽度——
§10.9 已经裁定宽度不当能力代理。另有 **31 次 `judge: null`（其中 18 次确定性层是过的）被静默放行**，
等于那 18 个 PASS 少了一半评分标准。据此把裁判收敛到**只剩来源问题**：

| 处置 | 题 | 理由 |
|---|---|---|
| 删 rubric（10 道） | locate-bug-001~008、debug-stacktrace-010、script-dev-007 | 细则索要的东西确定性判据已逐条覆盖（答案键、必读文件、测试/grep 证据、产物精确数值） |

唯一要认账的损失说清楚：那 1 次翻转发生在 `locate-bug-006`，题面第 23~24 行确实写着
「grep 至少两次、至少阅读 5 个文件」，而 §10.9 把这类宽度从闸门里撤了——裁判当时执行的
是一条**已声明但不再被判定**的要求。删掉 rubric 后它彻底不再影响分数；题面那句话保留，
因为它是达成目的的可行路径提示，只是我们已裁定它不当能力代理（同一处理适用于 §10.9 动过的
全部 31 个题面）。
| 留 rubric + `judge_id`（7 道） | data-pipeline-007/008/009、memory-loop-001~004 | 产物全对**也可能**是硬编码或对 read_file 片段的估算；终态看不出来源。N1（扰动输入复算同一脚本）建成后应替换并删除 |

裁判侧同时钉死：`temperature=0` + 固定 seed（档案写 null 也覆盖），`judge_id` 进
`task_fingerprint`（`judge.py` 也进了 `_FRAMEWORK`），实跑档案与题面不符或没评成一律
`graded=False`——**未评既不是通过也不是失败**。代价说清楚：这 10 道题从此不再产出
`rubric.*` 维度分，报表少 10 个主观维度；换来的是 43 道题纯确定性可重复。

验证：`python3 tools/test_infra_retry.py` 33/33（mock server 打真实 httpx 路径、
假 provider 打真实 run_task 路径、真实 CLI 探针打死端口），`tools/apply_rubric_triage.py --check`
状态一致，全 50 题两不变量复跑见 §10.12。指纹因 `_FRAMEWORK` 变更而全量重算，
`runs/` 里的历史按旧指纹保留、不再与新分数同榜比较。
