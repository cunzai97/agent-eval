# 两条不变量：可解 与 可重复

本套件的每一道题都必须同时满足：

1. **可解**——只读 `task_prompt`（含 system prompt 与环境内可见文件）就能构造出让全部
   `success` 断言通过的解。不依赖任何模型的临场发挥，也不依赖"以前有模型蒙对过"。
2. **可重复**——同一条解重跑，判定与终态逐字节一致；不依赖墙上时钟、机器快慢、
   本地时区、网络可达性或并发负载。

这两条不是愿望，是有闸门的：

    python3 tools/audit_invariants.py --jobs 4 --json .scratch/invariants.json

退出码非零表示有题不成立。**每次改完题目或环境都应重跑一次**，它约 20–40 分钟。

## 闸门怎么取证

| 检查 | 做法 | 不成立时的含义 |
| --- | --- | --- |
| 可解 | 优先把历史判对的轨迹灌进**当前**闸门重跑 `run_checks`；没有可用历史时，改跑 `docs/hardening_evidence/references/<task>.json` 里的参考解 | 题面不足以推出解，或闸门加过了头 |
| 可重复 | 同一条解**跑第二遍**，比对判定与终态 SHA-256 | 环境或断言里有 nondeterminism |
| 静态隐患 | 扫快照与隐藏测试里的未播种 `random`、`datetime.now`/`time.time`、本地时区、网络与 `sleep` | 换机器/换时刻结果会漂 |
| 计时依赖 | 禁止任何 `state_assert` 读 `summary`/`elapsed_s`/`latency_ms`/`duration` 一类字段 | 判定随机器快慢翻 |
| 资产在位 | 解析快照的 `source.json`，确认指向的文件存在 | 题目当场不可解（liberty 踩过） |
| 预算余量 | 报告历史通过轨迹用掉的最大 steps/tokens/elapsed 对比题面 budget | "超时"会伪装成"能力不足" |

## 参考产物是什么

`docs/hardening_evidence/references/<task>.json`：一份**脚本化的正确解**，
`{"calls": [[tool, args], ...]}`，只准用该题 `agent.tools` 里声明过的工具，
由审计器灌进全新快照后交给该题自己的 `run_checks` 判定。

它存在的理由是：历史轨迹证明的是"有模型做到过"，参考产物证明的是"**题面足够做到**"。
后者才是可解性的定义。`docs/hardening_evidence/negative_controls/` 则是反向证据——
可见测试全绿但语义没修的捷径，必须失败。

### 已修的第二处：解释器浮动标签

`shell_ws`（8 道题，含全部 script-dev 与 write-cli）的 `run_bash` 与 held-out 用例原本跑在
**`python:3-slim` 这个浮动标签**上，本机它解析成 Python 3.14.5。以后重新 `docker pull`、
或换一台机器，解释器就可能换 minor——`round()`、字典序、时区数据这些行为真会变，
而隐藏用例的 `EXPECTED` 是在某个具体解释器上实测出来的。code_repo 那侧反倒没有这个毛病，
它用的是本仓库 `docker build` 出来的 `agent-eval-pytest:3.12`，内容由 Dockerfile 固定。

现在两边都收敛到 `evalkit/envs/sandbox.py`：第三方镜像按 **digest** 钉
（`python@sha256:c845af93…`），自建镜像保留标签。改任何一边的镜像都要同步这里的
`SHELL_PYTHON_VERSION` 注释，并且**必须重跑 `EXPECTED` 的实测来源**——
`evalkit/envs/shell_hidden.py` 的 `EXPECTED` 不是手抄的，换解释器就是换事实基准。

### 已修的一处：pytest 计时尾污染终态

`evalkit/envs/code_repo.py::_parse_pytest` 把 pytest 的最后 12 行连同 **`8 passed in 0.01s`**
一起存进 `state.test_report.summary`。同一份解两次重放，终态就会因为这个计时尾不同。
判定用的 `passed/failed/errors` 计数不受影响，所以它在低负载下几乎不出现——
只在耗时跨过 0.01s 边界时翻脸，属于典型的"并发一上来就复现"的隐性 flake。
现在计时尾被剥掉，终态恢复可哈希复用。

## 已修的一处可解性缺陷：grep 的 path 限定与工具说明矛盾

`code_repo` 的 `grep` 说明写着"可限定 path"，实现却只接受文件：`path` 给目录时
`os.path.isfile` 不成立，**静默返回空结果，但 `grep_calls` 照样计数**。信了说明的 agent
会把有限的取证预算花在空结果上，最后合理地面推出"这个符号不存在"。locate 一系题有
`grep_calls >= 2` 与证据门槛，这直接关系可解性。

现在目录 `path` 会展开为该子树的文本文件，路径不存在则明确报错（`ok=False`），
不再给出"成功但为空"这种会误导的信息。实测：目录/文件/全仓三种限定都能命中，
坏路径返回错误而不是空结果。

同轮还查出快照里残留 `.pytest_cache/v/cache/lastfailed`——它把失败的测试名在 agent
复现之前就泄露出去，削弱"必须先跑测试"的证据门槛；`locate-003` 的那份甚至列了一个
当前**通过**的用例，等于指向错误答案的假线索。它被 `.gitignore` 排除也不进指纹，
所以只影响本机。现在 setup 阶段统一清除，`environments/` 下现存的污染目录已删。

## 实跑读数发现的第三类缺陷：题面自相矛盾（闸门看不见）

`memory-loop-005` 是本轮唯一被 1235 实跑读出问题的题。它的 `docs/runbook.md` 第 1 条原文是
"结算基准日 = 当月的**最后一个结算工作日**，即最后一个既在当月、又不出现在 `config/holidays.md`
里的日期"——括号把"工作日"定义成了"不在 holidays.md 里"。而 2025-06-28 是周六、06-29 周日、
06-30 周一（`holidays.md` 里那条"端午调休"正是为它准备的），数据里 9999/7777/-8888 三个诱饵
恰好压在 06-28/29/30 上。出题意图是 **06-27**（最后一个周一至周五且不在 holidays 的日期），
但按题面字面读出来是 **06-29**。同一份题面里两个定义给出两个答案，`EXPECTED` 只承认其中一个。
第 3 条同病：分号串起来的"保留最大修订；cancelled 剔除；按日期过滤"，按字面顺序执行会剔掉 T3，
而 `EXPECTED` 要 T3 的 700.50 ——即"先剔 cancelled 再去重"。模型严格按题面读，两问全错。
处理方式见本节末："只动不符合逻辑的地方"——`runbook.md` 两处定义写明（工作日=周一至周五；
三步口径按 cancelled→日期→去重 的顺序），**`EXPECTED` 一个字没改**。

**为什么两不变量闸门抓不到它**：可解性只有两条证据通道——历史判对轨迹回放、人工参考产物。
参考产物证明的是"存在一条动作序列能过闸门"，它编码的是作者已知的意图，不是题面能唯一推出的结论。
题面自相矛盾时参考产物照样报 `SOLVABLE+STABLE`（005 就是这么"通过"的）。
所以这道闸门对"判据可满足 + 终态可重复"是硬的，对"仅凭题面能否唯一确定答案"是盲的。
要闭这个缺口只有两条路：把模型真跑一遍读轨迹（本轮走的就是这条），或者加一个"题面唯一解"探针
（把题面喂给独立求解器，比对它推出的答案与 `EXPECTED` 是否一致）。后者每多花一次就要多付一次
推理开销，暂时按需在改动题面时手工做。

同一轮里第三个同类（也更隐蔽的）实例是 `debug-stacktrace-009` 的**流程判据考了题面没说的东西**：
它的 `order_of [run_tests, edit_file, run_tests]` + `run_tests >= 2` 要求改动前先跑一次基线，
而它的 system prompt 写的是"先读 README 与源码确认所有登记点，再改源码并用 run_tests 验证"——
读→改→验，压根没有基线这一步。基线那句只存在于 `debug-stacktrace-010` 的提示词里，
判据是从 010 抄过来的。实跑的 009 把 README 的 10 个登记点全找齐、7 处编辑、反向 grep 自查、
改后复跑 9 条全绿、**7 条隐藏用例全过**，只因为没做那次基线而被判 FAIL。

等价的缺陷在 `fix-failing-test-009`（"先用 grep 逐个核对调用点，再修源码并用 run_tests 验证"）。
`fix-failing-test-008` 不算：它的"先复现"确实隐含了改动前要把失败跑出来。

这两处的处置与 memory 五题一致：**把契约写明，判据一个字不放松**。顺带按历史数据核了这两种
流程约束各自携带多少能力信号（103 条带隐藏用例的 debug/fix 尝试，"结果性断言全过"为分母）：

| 形态 | 样本 | 结果性断言全过 |
|---|---|---|
| 从没跑过测试 | 10 | 0 (0%) |
| 只建基线、改完没复跑 | 4 | 0 (0%) |
| 改后复跑 + 有基线（题面原要求） | 81 | 30 (37%) |
| 改后复跑 + 无基线（009 这次的形态） | 8 | 4 (50%) |

也就是说"改完必须复跑"是有信息量的（不满足者 0/14 全错），"改动前必须有一基线"在这批数据上
测不出能力差异（无基线那一组反而略高，但 n=8 撑不起结论）。所以基线这条现在是以
**已声明的工程纪律**在计分，不是以能力代理在计分——要把它换掉的话，换成 `order_of
[edit_file, run_tests]` 就足够覆盖真正有信号的那一半。

两处的处置同向：**只把题面没说清的规则补上，判据一律不放松**——005 的 `runbook.md` 写明两处定义
（工作日=周一至周五；三步口径按 cancelled→日期→去重），009/fix-009 的提示词写明"先建基线"，
而 `EXPECTED`、隐藏用例、`order_of` 全都一个字没改。改的是题面与判据的一致性，不是难度。

## 同轮被纠正的一次误判：判据过严不等于该松

顺着 005 的轨迹我看到 `write_calls == 0` 罚了"另外记了一条不冲突的新口径"，
而系统提示词写着"将新验证且可复用的结论写入记忆"，于是把 `memory-loop-001~005` 的
记忆计数断言一并放松了。这个改法是错的：记忆闭环要考的正是**一次闭环只留一次记忆变更**，
放松它就是把题做软。已经全部回退为原样（`update_calls == 1 and write_calls == 0`、
`version == 5/2`、`write_calls == 1 and update_calls == 0`、`write + update == 1`），
改为把这条契约**写进题面**：五题的 system prompt 现在明确"一次任务只允许一次记忆变更；
被证据推翻的旧记忆用 memory_update 原位改写，不得另写并存的新条目；只有记忆里本来没有
对应条目时才 memory_write"。这样判据既严格又是"遵循已声明契约"，不再是猜出题人的偏好。
按 §10.3 的口径记账：这条属于契约遵循考点，不算排障考点，也不计入存活率变化——
001/002/003 在回退后的闸门下历史存活仍是 **20/20、19/19、23/23（100%）**，与改动前一致。

005 只留下一处真正的松绑：删掉 `'2025-06-30' not in content`。正确的修正恰恰要说明
"06-30 是端午调休所以不算"，禁止**提及**某个日期是关键字检查而不是逻辑检查，
防"没改而是另写一条"的活由 `version == 5` + `by_key[旧key].content` 承担。

## 实跑读数发现的第二处缺陷：一次最普通的 read_file 就能撑爆上下文

`data-pipeline-008` 两次实跑都在"step 1"就 400，`tokens=1236` 看着像基建抖动。用
`tools/probe_request.py --task data-pipeline-008 --turns 2` 把响应体打出来才看到真因：

```
{"error":{"code":400,"message":"request (184397 tokens) exceeds the available context
 size (99072 tokens)","type":"exceed_context_size_error","n_ctx":99072}}
```

`agent_loop` 的步数下标从 0 开始，所以"step 1"是**第二次**请求——第一次 `list_files` +
`read_file` 成功了，`read_file` 把 440,150 字节的 `daily_bars.csv` 按旧上限
`f.read(200_000)` 整块塞回观测（205,977 字符 ≈ 184,397 token），下一次请求必然超上下文。
模型什么都没做错，题也没做错，是**环境的观测尺寸**让这道题在任何模型上都不可解；
而判定层把它记成 `passed=false`，与"能力不足"混在同一格里。

修法：`data_ws.read_file` 的返回上限收到 12,000 字符，并且**显式标注**
`truncated: true` + `file_bytes`，工具说明里写清这个契约。取值口径写死在注释里：
12k 字符 ≈ 11k token，即使 64k 的题面预算已花掉大半，单条观测也不足以把请求一次性推过
99k；同时它够放 ~1000 行 CSV，"片段看起来很有代表性"这个陷阱本身一点没削弱——
008 的题面本来就写着"read_file 一次装不下它"，把隐性地雷改成可读契约不算送分。
`large_file_ws` 的同款 200_000 上限量过之后确认打不着（`_abspath` 不许越出 work_dir，
66 MB 的 .lib 是外部源文件，只能走 `source_*` 那套有预算的通道），所以没动它，
免得白白换掉 liberty 题的指纹。

顺带记一条仍未修的判定层缺陷：**上游 4xx/5xx 会被直接折算成任务失败**。
`evalkit/provider.py` 用 `raise_for_status()`，异常文本里只有状态码没有响应体，
`evaluator.py` 又把 `termination == "error"` 记成 fail。上面这个 400 之所以能定位，
是因为我在仓库外临时写了探针。把响应体带进 `traj.error` 需要改 `provider.py`，
而它在 `_FRAMEWORK` 里（一改全部 50 题指纹就变，正在跑的对照会裂），
所以留作待决项，见 §待你决定。

## 隐藏测试自己也会写错：罚"解释得更清楚"的子串判据

`script-dev-008` 的三条隐藏用例共用一个入口检查，旧实现是

```python
if "project" in text: raise AssertionError("run.sh still references the non-existent project/ directory")
```

对整份 `run.sh` 做子串匹配。模型把 `cd project` 正确改成了 `cd pipeline`，并在注释里写明
"交接稿误写为 project/"——**一句更负责的说明让它三条用例全挂**，而 `bash run.sh` 实测退出码 0、
报表照常生成。函数自己的 docstring 还写着 "Any shell shape is accepted"，实现与意图相反。

判据罚了正确答案，属于不逻辑，不是难度。现在拆成两问：(1) 在工作区副本里真的 `bash run.sh`，
要求退出码 0 且生成非空 `out/report.csv`（先删掉已有报表，"能生成"才是证据）；
(2) 只在**非注释行**上解析 `cd` 的目标并检查目录真实存在，挡"只改注释不改命令"。
五个方向的验收（全部实测，不是推理）：

| 工作区形态 | 隐藏结果 | 判对了什么 |
|---|---|---|
| 实跑解：命令行改对 + 注释提到 project/ | 3/3 | 原来的假阴性消失 |
| 原始快照：`cd project` 未动 | 0/3 | 未修 |
| 只加注释、命令行仍是 `cd project` | 0/3 | 症状修 |
| `cd` 到存在但没有入口的目录 | 0/3 | 改错了地方 |
| 命令行改对但 `main.py` 仍按 CWD 解析路径 | 0/3 | 题面另一问（路径要按脚本自身位置解析）仍在考 |

shell_ws 全族 8 题复跑 SOLVABLE+STABLE（新增的那次 `bash run.sh` 只跑在副本里，终态不受影响）。
同一轮的第二个提醒是**预算自洽性**：`liberty-extract-001` 实跑 15 步就把 900s 花光，
token 只用到 37,127/64,000，绑定约束是墙钟——长上下文下解码从 ~70 tok/s 掉到 ~17.8 tok/s。
该题历史 0 条尝试，所以把 `timeout_s` 提到 1800 不移动任何已考过模型的 goalpost，
只是让"跑不完"不再被记成"不会做"。这类"64k token 与 900s 在本地 27B 上不可能同时用到"的
不自洽，应当逐题核；闸门里的 `budget_headroom` 只在有历史样本时才算得出来，新题必须靠实跑。

## 两个结构性问题：已裁定并落地（2026-09-21）

裁定原话：『模型要能够重试才行，然后裁判还是需要的，只不过确定性的东西就不需要裁判了』。
实施与残余风险记在下面，别把这一节当成"已彻底解决"。

### 一、上游故障不再折算成"模型没做对"（已修）

1,436 次已录尝试里 76 次 `termination=error`，75 次是纯机器问题（48 refused / 22 5xx /
4 断连 / 1 超时），且集中在 3 个跑批夜各砸一个模型——最狠的一行 25/65 次被机器吃掉，
按"未评"重算 31 个模型里 19 个名次会动。现在的口径：

- `provider._with_infra_retry`：可重试故障（连不上 / 5xx / 429 / 断连 / 读超时）指数退避，
  默认 4 次；**重试不得吃掉本题剩余墙钟**，预算用完仍归 `timeout`（那是模型太慢）；

## 已裁定：改完不复跑算模型问题，判据不动（2026-09-21）

`debug-stacktrace-010` 出现过一次这样的失败：可见 9/9、隐藏 8/8、改对了文件、没碰 `tests/`，

理由与边界，供以后同类情形直接引用，不必重新人工确认：

## 榜单准入：套件长大之后，旧行怎么处置（2026-09-21 修复）

现象：模型排名整片消失，只剩新基线一行。根因在 `web_server.py` 的历史快照兜底层——
它的注释写着"当前完整 run 不该让旧模型全部消失"，条件却是
`expected == len(MANAGER.tasks) and total == len(MANAGER.tasks)`，即要求旧 run 也是**当前 50 题**。
40 题时代的完整跑分因此一行都不满足，兜底等于没兜。

改成：历史层收"按自己那一版题集算作完整"的 run（`expected == total`），并加一道地板
`expected * 2 >= 当前题数`。地板是必要的——第一版我只去掉题数条件，结果三条 1 题冒烟跑
以 `1/1 = 100%` 压在了 40 题整套跑前面。

另有一条我自己的操作教训：改完某题题面后**必须重启控制台**。`MANAGER.tasks` 在进程启动时缓存，
不重启的话它拿旧题面算指纹，会把刚复跑的那题判成 stale，进而让整行从"当前层"掉进"历史层"。
这次就是它把新基线也挤下去的。

读数纪律不变：历史行与当前行**不可比**（题集 40→50、隐藏闸从 9/40 到 27/50、旧口径把基础设施
死亡记成能力失败、裁判从 17 题收到 7 题）。UI 把它们标成"历史配置快照"并附来源 run id；
要在新指纹上重建排序，只能把其余模型各跑一行。


## 判定标准：理论上可解，不是零歧义（2026-09-22 裁定）

题面**允许**误导、允许留白。"判据钉了某件事而题面没写"本身不构成缺陷——只要模型能从它看得见的信息里推出来：
工程惯例、题面用词、随发代码的对照、`list_files`/`read_file` 一步即见的事实，都算可解。
2026-09-22 我提了 4 条 B 类 + 12 条 A 类"补题面"建议，被按这把尺重判，只剩一条成立。用户原话：
『题目允许有错误干扰，只要求题目是理论上可解就行』。

**唯一算缺陷的形状：判据依赖模型在任何可见信息里都拿不到的事实。**
已修的一例：held-out shell 用例把结果要求写进 `held/`，而题面与可见示例里只出现过 `out/`，
"CLI 必须自建 `--out` 父目录"看不见也推不出 → 现在由 `Scenario.prepare()` 预建 outs 的父目录
（只建目录，`FIXTURES`/`EXPECTED` 未动）。前后：9B 在三题上的隐藏用例从 0/6、0/6、0/8 变成
4/6、1/6、7/8，**这才是它自己的错**；已判对的轨迹重放后仍全绿，0 例翻转。
被判定为"合法难度、不动"的例子：locate-004 题面那句"五个关切分别在不同模块"（`list_files` 一步看穿）、
fix-008 要求 `ValueError`（27B 本轮 5/5 交卷，即可证可解）、fix-003 分隔符全集、`order_of` 里
`write_file`/`read_file` 的前置、memory 题要求记忆正文点名字段。

**推论：方向是加固，不是消歧。** 判据与设题说明打脸时（debug-005 要求改 `funcs/state.py`，
而隐藏文件自述"刻意不断言它的形状"），正确动作是**给这条 gate 补一条可观察用例**，不是删 gate；
被环境预先满足的恒真分支（memory-003 的 `tags` 析取、script-008 的 `'run.sh' in state.files`、
liberty 的 `preview_bytes<=160000`）应当收紧；题面声明了却没数据触发的规则
（clean-aggregate-001 的"先去重再过滤"、`YYYY/MM/DD`）要补触发样本。

## 实测通过率的分母：题面变更过的旧结果也不算数（2026-09-23）

`web_server.measure_by_task()` 给看板每题算"实测通过率 = 1 − 实测难度"。规则与判定层同源：
**分母只收对当前题面成立的能力判定**，未评（上游故障 / rubric 未评成）和 stale（那次运行之后
题面或框架变过、指纹已不符）都排除在外，但各自单独计数，缺了多少要看得见。

这条之前是写错的（只排了未评），代价当场可测：50 题里 **48 题的通过率被这次修正改变**，
`memory-loop-003` 从 6.8% 变成 100%（3/3 已判定，另有 40 次是 09-21 重建指纹之前的旧版本），
`debug-stacktrace-008` 从 1/44 变成 0/4。也就是说按旧的板子排序，"最难的题"其实是
"被题面变更污染最多的题"，而真正的难题（008）被挤到中列。09-21 那批任务加固 + 指纹重建留下的
约 40 次旧结果全都在这个坑里。

**同一个坑的另一半**：`passes` 也不能收 stale 的通过。旧版本上做出来过，不等于当前版本做得到——
反过来也一样。所以 pass 和 fail 双向排除，只有 tokens/步数照旧全收（成本量的是那次运行花了多少，
